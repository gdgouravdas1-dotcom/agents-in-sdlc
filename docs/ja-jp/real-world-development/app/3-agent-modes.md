まず、プロジェクトに小さな機能を追加しました。しかし、より大規模な変更には、さらに堅牢なプロセスが必要です。GitHub Copilot app は組織の既存のフローに沿って作業し、適切なものを適切な方法で構築できるようにします。このレッスンから数回にわたり、Issue を使った新機能の作成から、コードと機能の検証、プロジェクトへのマージまで、一般的なエージェント主導の開発プロセスを実践します。

> [!NOTE]
> 機能のワークフローを進める間は、同じセッションを使用します。通常は作業するファイルの種類ごとに異なるセッションや PR を使用しますが、ここでは中心となる概念に集中できるように手順を短縮します。

このレッスンでは、次のことを行います。

- GitHub Issue から新しいエージェントセッションを開始します。
- **Plan** モードで要件を定義します。
- **Autopilot** モードを使用して新機能を実装します。
- コードをレビューします。
- ブラウザー キャンバスで機能を手動検証します。

この機能の作業を続けながら、リポジトリの指示を更新し、既存の quality-checks スキルをカスタマイズして、MCP による検証を追加し、QA エージェントを作成して、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが成長し、訪問者がカテゴリと出版社でゲームを絞り込む機能が必要です。バックログの Issue に機能は記載されていますが、カテゴリの組み合わせ方などはコーディング前に合意が必要です。Plan モードで決定事項を整理してから、Autopilot による範囲を限定した実装を承認します。

## 背景

AI コーディング エージェントを開発フローに導入しても、基本は変わりません。むしろ、基本はさらに重要になります。多くの開発者は、次のようなフローに従います。

1. 必要な作業の詳細が記載された Issue を開きます。
2. 構築する内容の計画を作成します。
3. コードを構築してレビューします。
4. テストを実行してコードを検証します。
5. 新機能を手動で検証します。
6. プルリクエスト (PR) を作成します。
7. コードのレビューと継続的インテグレーション プロセスが成功したら、コードをマージします。

> [!NOTE]
> 正確な手順はチームや組織によって異なりますが、多くの場合は上記の流れを変形したものです。

この標準的なアプローチを守ることで、AI が生成したコードが定められた要件を満たし、人間が作成したコードと同じ審査プロセスを通るようにできます。

## セッションモード

**セッションモード**は、エージェントの自律性を制御します。プロンプト フィールド下のドロップダウンから設定し、いつでも変更できます。

- **Interactive**: エージェントと一緒に作業します。エージェントは変更を提案し、続行前に入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントが自律してコードの作成、テスト実行、反復を行い、入力を待ちません。

Plan モードで開始し、計画をレビューしてから、Autopilot で実装します。

## Issue からセッションを開始する

開始前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys のリポジトリ フォルダーを選び、リポジトリの上部ナビゲーションから **Issues** を開きます。既存の **Allow users to filter games by category and publisher** を開きます。テンプレートで用意された Issue のため、新たに作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選びます。

   ![GitHub Copilot app の Issue ビューで、New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに添付されていることを確認し、モード セレクターで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行させます。ターミナルでは動作してもセッションで見つからない場合は、アプリの PATH またはバージョン マネージャーの設定を確認してから、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで再インストールしないでください。

## フィルター機能を計画する

計画を立てることで、Copilot がコードを書く前にアプローチをレビューできます。Issue から開始したため、Copilot は機能のリクエストをすでにコンテキストとして持っています。次を送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、Issue の受け入れ条件と計画を照らし合わせます。カテゴリと出版社による絞り込み、アクセシブルなコントロール、データ アクセスの変更、テストが含まれていることを確認してください。複数カテゴリの組み合わせ方や、一致するゲームがない場合の動作など、不明確な点について話し合います。

計画には、プロジェクトの既存ツールを使った lint、ユニット テスト、E2E テスト、型チェックを含めます。フィルター機能の実装とテストに範囲を絞ってください。PR は品質ワークフローの完了後に作成します。計画の修正は承認前に依頼し、後の検証に使えるよう Issue の URL と合意した追加の取り決めを控えておきます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan**、または使用中のバージョンで表示される同等のオプションを選択します。承認によってモードが切り替わると思い込まず、現在のモードを確認してください。モード表示が **Autopilot** であることを確認します。

Copilot が実装を開始します。計画に沿ってコードを生成し、テストを実行しながら、作業を反復します。

> [!NOTE]
> 承認するとすぐ実装が始まる場合があるため、先に計画をレビューしてください。依存関係の不足やポート競合が報告された場合は、チェックを完了と判断する前にセットアップの問題を解決します。停止してよいのは、自分で起動したサーバーだけです。

## 実装をレビューして検証する

生成されたコードも、ほかのコードと同様にマージ前のレビューが必要です。

1. **Changes** を開き、フィルター機能の実装とテストを確認します。
2. 複数カテゴリと出版社の組み合わせも含め、結果を Issue と承認した追加の取り決めに照らし合わせます。変更が既存のリポジトリの指示に従っていることを確認します。
3. lint、ユニット テスト、E2E テスト、型チェックの結果を確認します。スキップされたチェックは成功ではありません。
4. 実装を承認する前に失敗を解消し、該当するチェックを再実行します。Playwright の E2E 設定はビルドしてプレビューを配信し、ローカル サーバーを再利用できるため、テスト対象が以前のレッスンではなくこの worktree のサーバーであることを確認します。

## 新機能を確認する

コードに問題がないように見えても、実際に動くでしょうか。前と同じようにアプリを起動し、ブラウザー キャンバスでサイトを開きます。

1. 次のプロンプトを使い、アプリを起動してブラウザー キャンバスで開くよう Copilot に依頼します。

   ```plaintext
   Start the app and open it in the browser canvas.
   ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザー ウィンドウが開きます。
3. カテゴリを選び、結果がそのカテゴリと一致することを確認します。フィルターを解除し、出版社を選んで結果を確認します。
4. カテゴリと出版社を組み合わせ、結果を Issue と承認した計画に照らし合わせます。複数カテゴリに対応する場合は、合意した組み合わせの動作を検証します。
5. ゲームが見つからない組み合わせを試し、空の状態を確認します。フィルターを解除またはリセットし、一覧全体が戻ることを確認します。
6. 終了したら、次のプロンプトでこのセッション用に起動した開発サーバーを停止します。

   ```plaintext
   Stop the dev server and close the browser canvas.
   ```

## 次のレッスンのためにこのセッションを保持する

フィルタリング PR はまだ作成またはマージしないでください。レッスン 4 から 8 でも、このセッション、worktree、ブランチを使います。次はカスタム指示をフィルタリング コードに適用し、スキルと QA の改善を追加してから、レッスン 8 でまとめた PR を作成してマージします。開発サーバーを停止したら、セッションをそのままにしておき、次のレッスンで再開してください。

## まとめと次のステップ

さまざまなエージェント モードを使って機能を構築し、レビューしました。

- GitHub Issue から新しいエージェント セッションを開始しました。
- **Plan** モードで要件を定義しました。
- **Autopilot** モードで新機能を実装しました。
- コードをレビューしました。
- ブラウザー キャンバスで機能を手動検証しました。
